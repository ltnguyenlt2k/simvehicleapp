# ADR-0030: AI Assistant thay Copilot — chat + provider từ `.env` + MCP server/client + WorkflowPatch

- **Status:** Proposed · **Date:** 2026-09-30 · **Level:** L1
- **Related:** FR-AI-01..05, FR-CG-07, R20; [09](../09-ai-assistant-mcp.md); [00 F3](../00-research-findings.md#24-phát-hiện-quan-trọng--lệch-so-với-master-plan-v2)

## Context
Copilot của Sim phụ thuộc backend độc quyền `copilot.sim.ai`. PO muốn khung chat, API key từ `.env`, tích hợp MCP, prompt để sinh & điều khiển workflow. Master Plan giới hạn AI không sinh code production.

## Decision
1. Service riêng `ai-assistant` (repo `simvehicleapp-ai`, TS/Bun). Studio chỉ có Chat UI + render patch preview.
2. Provider adapter tái dùng code `apps/sim/providers/*` (Apache-2.0), tách khỏi Next.js; chọn bằng `SV_AI_PROVIDER` + `SV_AI_MODEL`; hỗ trợ tool calling + streaming. **Định dạng canonical nội bộ (mới, xem Notes):** dùng thẳng **content-block shape của Anthropic Messages API** (`text`/`tool_use`/`tool_result`) làm biểu diễn chuẩn duy nhất cho lịch sử hội thoại, tool schema, và kết quả stream — mọi provider khác (OpenAI-compatible, Gemini) **dịch** request/response của chính nó sang/từ shape này ở lớp adapter, thay vì phát minh một schema canonical mới. Lý do: tái dùng một schema đã thiết kế tốt, giảm số loại dữ liệu phải lưu/test. `GET /capabilities`-style `LlmProvider.streamTurn({system, tools, messages, onText}) -> {content, stopReason}` là interface tối thiểu mỗi adapter phải cài.
   - Provider `gemini` **PHẢI** gọi API gốc của Google (`generativelanguage.googleapis.com/v1beta/models/{model}:streamGenerateContent`, header `x-goog-api-key`), **KHÔNG** qua lớp OpenAI-compatible của Google — xem Notes (khác biệt định dạng API key, đã verify bằng key thật).
   - Provider `openai-compatible` dùng cho mọi backend nói chuẩn OpenAI Chat Completions (`POST {base_url}/chat/completions`, có `tools`): OpenAI thật, Azure OpenAI/AI Foundry, OpenRouter, **hoặc một server LLM tự host (Ollama/LiteLLM/vLLM) chạy ở máy/mạng khác và trỏ `OPENAI_COMPAT_BASE_URL` vào đó** — không cần đổi gì khác trong code khi đổi giữa các backend này, kể cả khi đổi sang key/nhà cung cấp khác.
3. **MCP server `simvehicleapp`** (SDK `@modelcontextprotocol/sdk` — **v1.x** (xem Notes, không phải v2.x như từng ghi nhầm), transport Streamable HTTP tại `/mcp`, bearer token) định nghĩa toàn bộ tool ([09 §4](../09-ai-assistant-mcp.md#4-bộ-tool-mcp-simvehicleapp-v1)); agent loop nội bộ dùng chính tool registry này (in-process).
4. **MCP client**: kết nối server ngoài từ `SV_MCP_CLIENTS` (JSON), tool ngoài được namespace `ext.<name>.*`, mặc định cần xác nhận.
5. **WorkflowPatch v1** là cách duy nhất AI sửa workflow; luôn validate trước khi hiển thị; user Accept mới apply (flag `SV_AI_AUTO_APPLY_DRAFT` cho draft).
6. **Cơ chế xác nhận tool có side-effect — cụ thể hoá (mới, xem Notes):**
   - Mọi tool MCP được gắn nhãn **tĩnh** `safe` (chỉ đọc) hoặc `sensitive` (ghi, hoặc tốn kém/khó hoàn tác dù không ghi — ví dụ `project_syncode`, `run_start`, `run_stop`, `signal_set` đều là `sensitive`) trong 2 tập hợp khai báo ở registry, **không** suy luận động từ tên/mô tả.
   - Tool `sensitive` không bao giờ tự chạy: agent loop trả về `pending_action {actionId, toolName, toolInput}`, **lưu ở backend** (không phải chỉ ở client) kèm TTL ngắn (gợi ý 15 phút), chờ `POST /actions/:actionId/confirm {editedInput?}` hoặc `/cancel`. `editedInput` của người dùng **luôn ghi đè** input mà LLM đề xuất.
   - **Chỉ 1 pending action đang hoạt động cho mỗi hội thoại** (lưu thêm một con trỏ hội thoại → actionId); khi đang có pending action, tin nhắn văn bản mới từ người dùng bị từ chối/điều hướng về xác nhận-hoặc-huỷ (vì giao thức tool-use của LLM yêu cầu mọi `tool_use` phải có `tool_result` trước khi hội thoại tiếp tục).
   - **Guard bắt buộc trước khi tạo `pending_action`:** kiểm tra `toolInput` so với `required` của JSON Schema tool đó; nếu thiếu field, **không** chuyển sang trạng thái chờ xác nhận — trả một tool-error bình thường để LLM hỏi lại/tự sửa trong cùng lượt. (Nếu bỏ qua bước này: LLM vừa hỏi làm rõ vừa phát `tool_use` thiếu field trong cùng lượt ⇒ câu trả lời của người dùng cho câu hỏi làm rõ bị nuốt mất vì hệ thống hiểu mọi tin nhắn tiếp theo là "xác nhận/huỷ".)
7. Chỉ container `ai-assistant` (và studio) có egress internet; codegen/compiler không. Kết nối MCP (cả nội bộ lẫn `ext.*`) mở **theo từng lượt chat, scope theo user**, đóng ngay sau khi lượt đó xong — không dùng connection pool dài hạn dùng chung giữa nhiều user.
8. Không có tool nào trả về/viết code C++/Python để đưa vào project.
9. **Rate limit theo user/session** (không theo IP, không dùng chung 1 hạn mức cho nhiều người) — mặc định `SV_AI_RATE_LIMIT_PER_MINUTE=20`, áp ở `ai-assistant` trước khi gọi LLM.
10. Kết quả tool MCP có hệ quả cụ thể (tạo project, bắt đầu run, sinh file...) **phải** trả `structuredContent` với field máy đọc được (vd `run_start` → `{runId, editorUrl}`) — không chỉ trả văn bản — để UI/agent ngoài dùng chính xác, không phải suy từ câu trả lời đã được LLM diễn giải lại.
11. `MAX_TOOL_ITERATIONS` mặc định **6** cho một lượt chat (không phải 12 như bản nháp trước), cấu hình qua `SV_AI_MAX_TOOL_STEPS`; log chi tiết lỗi tool ở server (kèm input/traceback) ngay cả khi câu trả lời hiển thị cho người dùng đã được rút gọn/diễn giải lại.

## Alternatives considered
| Phương án | Vì sao loại |
|---|---|
| Giữ Copilot Sim, đổi URL | Giao thức độc quyền, phụ thuộc hosted |
| Vercel AI SDK thay providers Sim | Cũng hợp lệ; chọn tái dùng providers Sim để giảm dependency — ghi chú: có thể chuyển sau nếu providers Sim quá dính Next.js (quyết định ở M10 task 1) |
| AI sửa workflow trực tiếp | Mất kiểm soát, trái Master Plan 3.3 |

## Verification
Test agent với LLM giả (scripted tool calls) ⇒ patch đúng; E2E với provider thật (nightly, optional key); MCP Inspector kết nối `/mcp` liệt kê tool; không có đường gọi LLM từ codegen (network test).
Bổ sung theo Notes 2026-10-02: (a) test tool `sensitive` thiếu field bắt buộc → nhận tool-error trong cùng lượt, **không** tạo `pending_action`; (b) gửi tin nhắn mới trong lúc có pending action → bị chặn/điều hướng về xác nhận-huỷ; (c) `editedInput` khi confirm phải thắng input gốc; (d) test provider Gemini với key định dạng `AQ.` thật → gọi thành công qua native API; (e) 21 request/phút từ cùng user → request thứ 21 bị rate-limit, user khác không bị ảnh hưởng.

## Notes / Deviations (2026-10-07) — M10, theo uỷ quyền PO 2026-10-06, chờ PO xác nhận
1. **T01 — provider: adapter `fetch` riêng, không dùng `apps/sim/providers` của Sim.** Provider của Sim nằm trong app Next.js (phụ thuộc store/executor/billing), kéo sang service riêng là import chéo module (luật cứng 2); SDK chính thức của từng hãng thêm 3 dependency cho việc chỉ cần một endpoint streaming. Adapter tự viết (`src/providers/`): Anthropic Messages (SSE), OpenAI Chat Completions (dùng cho `openai`, `openai-compatible`, `ollama` — `reasoning_effort: none` theo Notes 2026-10-02 §11), Gemini native (`streamGenerateContent?alt=sse`, header `x-goog-api-key`, §2). Biểu diễn chuẩn = content block Anthropic (§1); test bằng HTTP giả. Key chỉ ở container `ai-assistant` (env), `/status` không bao giờ trả key.
2. **Tool ngoài đặt tên `ext__<server>__<tool>`** thay vì `ext.<server>.<tool>`: Anthropic/OpenAI/Gemini đều chỉ chấp nhận `^[a-zA-Z0-9_-]{1,64}$` cho tên tool. Tool ngoài luôn SENSITIVE (đi qua xác nhận).
3. **WorkflowPatch hợp lệ chặt hơn compiler lint:** ngoài lỗi compile (`/compile` mode `verify` trên graph nháp), khối **mới thêm** mà không tới được từ trigger ⇒ `BLOCK_UNREACHABLE` mức lỗi (compiler chỉ cảnh báo — với đề xuất của AI, khối lơ lửng gần như luôn là patch sai), prop không có trong BlockSpec ⇒ `BLOCK_PROPERTY_INVALID`. Mã có sẵn trong catalog, không thêm mã mới. Tham chiếu `<ref.output>` mà model viết bằng id khối (`<b2.value>`) được viết lại thành tên chuẩn hoá (`referencesByName`) trước khi validate. Lỗi trả cho model kèm gợi ý sửa cụ thể (op `connect` còn thiếu, các tham chiếu tồn tại).
4. **Agent loop:** tối đa 6 bước; model "kể kế hoạch mà không gọi tool" trong khi hội thoại đang làm workflow ⇒ tối đa 2 lời nhắc nội bộ (`NUDGE_PREFIX`, không hiển thị cho người dùng) — model local nhỏ hay dừng ở mô tả. Lời nhắc tính vào số bước.
5. **MCP server:** Streamable HTTP **stateless** (`WebStandardStreamableHTTPServerTransport`, SDK `1.32.1` ghim chính xác như mọi dependency của repo — khác gợi ý `^1.x` ở Notes 2026-10-01, ghi `docs/BASELINE.md`), bearer token từ `SV_MCP_TOKEN` hoặc `SV_MCP_TOKENS` (token ↔ tên ↔ scope; không có token ⇒ `/mcp` tắt). Không có UI xác nhận ở client MCP ⇒ tool SENSITIVE trả lỗi `CONFIRMATION_REQUIRED` trừ khi token có scope `actions:auto`. `project_syncode` qua MCP cần ngữ cảnh studio (graph của project) ⇒ ngoài studio chỉ chạy trên graph đã lưu.
6. **Contract `ai-assistant.v1` bổ sung (additive):** `GET /status`, `context` (workflow + graph hiện tại, project + graph/scenario) trên `/chat` và confirm/cancel, `GET /conversations/{id}`, confirm/cancel trả SSE (lượt tiếp tục), 503 `not_configured`.
7. **Eval (T09) chạy trên model local** (Ollama `qwen3.5:9b` — không có key cloud trên máy dev); tiêu chí ≥80 % patch hợp lệ đo trên model này, ghi tỉ lệ và lỗi còn lại trong `docs/reports/M10.md`.
8. **License (ADR-0031):** mọi lượt gọi LLM (`/chat`, confirm, cancel) và mọi request `/mcp` đã xác thực hỏi PDP của orchestrator `GET /entitlements/ai.assistant` (endpoint mới, additive) — orchestrator vẫn là điểm quyết định duy nhất và ghi log. Từ chối ⇒ 403 `not_entitled`; PDP không trả lời ⇒ 503 (fail closed: không kiểm được license thì không chạy).

## Notes / Deviations (2026-10-02) — tham khảo kiến trúc agent/MCP thực tế từ repo riêng của PO

PO cung cấp quyền truy cập repo **private** `Blinkthor/web-blinkthor` (đọc qua `gh` CLI đã đăng nhập sẵn của PO, không phải nguồn công khai — không tái chia sẻ code trong tài liệu này). Phần liên quan: `packages/project-management/agent/` (service chat/agent độc lập, cổng `:8010`) + `packages/project-management/mcp-server/` (MCP server bọc domain API của chính họ), đang chạy thật cho một chat widget web **và** một bot Zalo OA (qua relay mỏng, xem dưới). Kiến trúc này **đã chứng minh được trong thực tế** các quyết định ở mục Decision §2, §6, §7, §9, §10, §11 phía trên; dưới đây là lý do cụ thể từng cái:

1. **Canonical content-block = shape của Anthropic**: repo tham khảo dùng thẳng type `Anthropic.ContentBlock` làm biểu diễn nội bộ duy nhất; provider OpenAI-compatible và Gemini đều **dịch** response của mình về shape này. Lịch sử hội thoại lưu Redis cũng theo đúng shape đó — không có một schema "trung lập" thứ hai nào phải đồng bộ. SimVehicle áp dụng y hệt.
2. **Gemini dùng native API, không qua lớp OpenAI-compat của Google**: tài liệu của repo tham khảo ghi rõ nguyên nhân — Google đang chuyển sang định dạng "Auth key" mới (key tiền tố `AQ.` thay cho `AIzaSy...` cũ), **key kiểu cũ ngừng hoạt động hẳn khoảng 2026-09**; đã tự tay verify bằng key `AQ.` thật: endpoint OpenAI-compat của Google từ chối key này ("Please pass a valid API key") trong khi API gốc (header `x-goog-api-key`) nhận bình thường. Đây là thông tin đã verify bằng key thật, không phải suy đoán — SimVehicle phải implement provider Gemini theo API gốc ngay từ đầu, không đi theo đường OpenAI-compat tưởng là tiện hơn.
3. **Phân loại tool tĩnh `safe`/`sensitive` bằng 2 tập hợp khai báo trong code** (không suy luận từ tên) — kể cả thao tác không ghi dữ liệu nhưng tốn kém/khó hoàn tác (ví dụ xuất báo cáo) cũng xếp `sensitive` để đi qua xác nhận trước khi chạy, không chỉ riêng "write vs read". Áp dụng trực tiếp cho bảng tool ở [09 §4](../09-ai-assistant-mcp.md#4-bộ-tool-mcp-simvehicleapp-v1).
4. **Bug thật đã gặp và cách phòng tránh** (nguyên văn lý do trong code của repo tham khảo): nếu LLM vừa hỏi làm rõ ("khoảng thời gian nào?") vừa phát ra một `tool_use` sensitive còn thiếu field bắt buộc trong cùng lượt, mà hệ thống lập tức chuyển sang "chờ xác nhận", thì câu trả lời tiếp theo của người dùng cho câu hỏi làm rõ sẽ bị nuốt (hệ thống chỉ hiểu nó là "xác nhận"/"huỷ", lặp lại hỏi mãi tới khi người dùng bỏ cuộc). Cách sửa: kiểm tra `required` của JSON Schema trước khi tạo `pending_action` — đã đưa vào Decision §6 ở trên như một yêu cầu bắt buộc, không phải tuỳ chọn.
5. **Một pending action/hội thoại, không phải một bộ đếm toàn cục** — do ràng buộc giao thức tool-use (mọi `tool_use` phải có `tool_result` kế tiếp mới gửi lượt mới được); repo tham khảo lưu thêm một "con trỏ hội thoại → actionId" trong Redis để enforce đúng 1 cái tại một thời điểm.
6. **Cho phép sửa input trước khi xác nhận** (`editedInput` luôn thắng input LLM đề xuất) — UX tốt hơn "chỉ Accept/Reject", áp dụng cho cả xác nhận tool side-effect lẫn WorkflowPatch (người dùng sửa nhẹ patch trước khi Accept thay vì phải Reject rồi gõ lại prompt).
7. **`structuredContent` trên kết quả tool MCP mang field máy đọc được**, tách biệt khỏi text LLM paraphrase — lý do nêu rõ trong code repo tham khảo: client gọi tool (vd bot Zalo) cần URL/ID chính xác để hành động (gửi ảnh thật, đính kèm đúng ticket), không thể tin cậy vào việc LLM không làm hỏng URL khi diễn giải lại thành văn xuôi.
8. **Rate limit theo token/user, tuyệt đối không theo IP hay dùng chung** — comment trong code repo tham khảo nêu rõ: dùng chung 1 token cho nhiều người sẽ làm họ tự giới hạn lẫn nhau.
9. **Kết nối MCP mở theo từng lượt, đóng ngay sau khi dùng xong**, header mang theo danh tính/quyền của đúng người dùng đang chat (không phải một credential dùng chung) — đơn giản, an toàn, đủ dùng ở quy mô này; SimVehicle áp dụng cho cả kết nối nội bộ (`ai-assistant` → `vss-catalog`/`compiler`/`orchestrator`) lẫn `ext.*` ra MCP server ngoài.
10. **Mẫu "relay mỏng cho nhiều bề mặt chat"**: bot Zalo của repo tham khảo không cài lại agent — nó chỉ mint một token phiên đúng quyền người dùng qua một bridge nội bộ (secret dùng chung giữa 2 service), rồi gọi **đúng** API SSE `/chat` mà web widget đã gọi, đọc cùng vocabulary sự kiện. **Khuyến nghị cho SimVehicle:** nếu sau này cần thêm bề mặt chat khác (Slack, Teams, Zalo…) cho AI assistant, làm đúng mẫu này — không bao giờ tạo bản sao thứ hai của agent loop.
11. **Ghi nhận thực nghiệm về "extended thinking"/reasoning**: bật chế độ suy luận mở rộng cho một model local trong chính vòng lặp tool-use làm **mọi bước đều tệ hơn** (một câu hỏi không cần tool mất 58 giây + 1548 token suy luận; bước trả lời cuối sau khi gọi tool thành công trả về rỗng 3/3 lần thử) — chỉ nên bật cho tác vụ một-lượt không có tool loop (nếu SimVehicle có tính năng tương tự, ví dụ "giải thích diagnostic"). Mặc định **tắt** reasoning trong agent loop chính.
